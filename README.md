# CSC592 JSON-update research and RPG Testing Workbench

This repository studies how reliably language models can update structured state from **an existing JSON document and new information**. It contains the prompt/test builders, a native-model Workbench, intent-parser libraries, evaluators, and saved research evidence.

## Start here

This is the navigation guide for the code on `main`. The current editable source is **[prompt_builder/templates/](prompt_builder/templates/)**. Its four folders are common, input_format, output_format and test_cases. The old test_builder code has been removed.

1. **Current research suite:** root [test_specs/](test_specs/) contains **21 cases across six current structured output formats**, generated by the file templates. Four cases cover each of Update, Append, Remove, Move and Copy, plus one no-change case. Three input presentations apply except that the no-array field update has two. The full suite has **372 distinct prompts and 372 observations per model at one repetition** (126 case/output definitions). Root Workbench discovers this suite; narrower requests must be explicitly labeled as subsets.
2. **Current reusable parser:** JavaScript, C# and Python support the custom five-operation language. The current research evaluator includes collection Move/Copy: append a complete independent copy to another collection, and additionally remove the source for Move. These are not RFC 6902 Move/Copy semantics.
3. **Historical evidence:** older definitions, schemas, prompts and model responses stay unchanged under archives/ and experiments/. They are not the new schema-free suite and their scores must not be relabeled.

The new build first passed exact legacy prompt parity, then deliberately removed schema hints. See [the migration evidence](archives/prompt-builder-parity/parity-report.json) and [current grading](docs/schema-free-evaluation.md).

## Prompt sources and generated prompts

### Current research prompts

- **[common/](prompt_builder/templates/common/):** shared rules, allowed changes, layout and selection. Layout comments identify the source of every placeholder and are not sent to models.
- **[input_format/](prompt_builder/templates/input_format/):** normal JSON, ID-keyed arrays, full paths and named tables. Each folder owns its explanatory text and selects its serializer. ID-keyed arrays use the [bracket-and-ID display](docs/id-keyed-input.md), not JSON objects or wrapper fields.
- **[output_format/](prompt_builder/templates/output_format/):** six current structured choices (`json_dot`, `json_slash`, `path_list`, `literal_line`, `end_marked_line`, `typed_lines`), each with its own complete instructions and reader selection. `format.json` records status. The superseded `two_line_text` and experimental `free_format` remain available only through explicit selection; they do not silently change the standard matrix. All 21 cases include custom Move/Copy support.
- **[test_cases/](prompt_builder/templates/test_cases/):** one human-named folder per case containing starting_data.json, requested_change.txt, expected_result.json, expected_patch.json and ID-only array_identities.json. No schema.json and no separate task-pattern source. Requested changes are read directly; reference answers are never sent to the model.
- **[builder.py](prompt_builder/builder.py):** file loading, compilation and installation. **[presentation.py](prompt_builder/presentation.py)** renders data, and **[template_text.py](prompt_builder/template_text.py)** fills layouts.

Edit wording in one source file, then compile without running models:

```sh
python -m prompt_builder --list
python -m prompt_builder --output build/prompt-suite
python -m prompt_builder --output build/prompt-suite --install
```

The last command activates the generated suite in root test_specs, preserving replaced definitions under archives/template-builds. A failed build leaves the previous complete build intact; prior successful builds are retained beside the output in a .history folder. Selection is explicit in common/selection.json or CLI arguments. common/coverage.json records the required suite, and build/install checks reject missing current coverage rather than silently shrinking “all.” Every build reports cases, input views, output formats, omitted combinations, distinct prompts, repetitions and observations. Explicit subset builds are labeled partial and require an explicit subset-install override before replacing the full active suite. Copying a case/format folder using an existing serializer/reader requires no Python edit; a completely new syntax needs a reader.

Pass/fail uses the final database with unordered arrays. A separate **expected-patch difference** flag shows alternative normalized patches without turning them into failures. Operation sequence remains ordered. `array_identities.json` names each array’s exact ID field, including custom names and empty arrays. Validation uses it, and the ID-keyed/full-path serializers use it internally to choose IDs. No map or schema description is added to prompts. Normal JSON presentation does not need it; the separate experimental named-table view retains its data-only `id`/`*_id` convention. Normalization receives no expected answer.

### Read the complete prompt actually sent

In a generated experiment directory, look for:

- `prompts/<test-id>/<presentation>.txt`: readable complete prompt.
- `prompts/<test-id>/<presentation>.messages.json`: exact API roles/content.
- `test_specs/<test-id>.json`: captured workflow, prompt bindings, variants, sampling, expected state and result contract.
- `manifest.json`: experiment identity, scope, prompt digests and exclusions where supplied.

For a completed observation, its captured request and definition are the authority, not today's edited template. Root [prompts/current-suite/](prompts/current-suite/) is the active generated preview. Older broad-suite previews are under [archives/pre-template-builder/](archives/pre-template-builder/). Edit source templates/data and use the appropriate exporter; do not hand-edit frozen evidence to match newer code.

## Intent parser, conversion and evaluation

### Reusable language implementations

| Location | Purpose |
| --- | --- |
| [intent-parser-js/](intent-parser-js/) | Readable reference implementation. `index.cjs` exposes prompt building, parsing, conversion and patch application as separate functions. |
| [intent-parser-js/intent.grammar](intent-parser-js/intent.grammar) | Canonical complete program/operation grammar, including component ordering, recursive groups, paths and JSON values. |
| [intent-parser-js/tokens.grammar](intent-parser-js/tokens.grammar) | Structural token-tree adapter used during semantic conversion, not the complete program grammar. |
| [intent-parser-js/build-grammar-spec.cjs](intent-parser-js/build-grammar-spec.cjs) | Generates `operation.grammar` and the shared grammar specification. Run it after canonical grammar edits; do not edit generated copies independently. |
| [intent-parser-js/GrammarForge/](intent-parser-js/GrammarForge/) | Vendored GrammarForge runtime used directly by JavaScript. |
| [intent-parser-csharp/](intent-parser-csharp/) | Native .NET 8 implementation, using the generated grammar specification. |
| [intent_parser/](intent_parser/) | Native Python implementation using the same generated rules; no Node/model/provider invocation is required. |

Read [GRAMMAR-DESIGN.md](intent-parser-js/GRAMMAR-DESIGN.md) for the boundary between grammar and code. State-dependent path resolution, ambiguous-role rejection, literal `add` interpretation, data safety and resource limits remain semantic checks. [ALIASES.md](intent-parser-js/ALIASES.md) records accepted/rejected spellings. These remain experimental libraries with explicit limits, not a claim of arbitrary text recovery or production readiness.

The generic API keeps parsing, conversion and updating separate. Custom patches are the default. `json_patch: true` selects standard RFC 6902 output **instead**; its indexed paths depend on the starting state and generated operation order. Custom Move/Copy semantics are not the same as directly emitting RFC Move/Copy. See each language's README for its API and limitations.

### Current live research integration

- **[evaluation/array_identities_intent.py](evaluation/array_identities_intent.py):** the current `array-identities-intent-v3` host. Every current response format uses the shared intent grammar before identity-based resolution, final-state grading and separate expected-patch diagnostics. Semantic normalization remains shared. Six strict format-specific validators independently check the requested serialization, without repairs or special cases; historical scores remain stored evidence, not new-parser results.
- **[evaluation/format_compliance.py](evaluation/format_compliance.py):** strict syntax compliance for the six active output types, recorded separately in `score.format_compliance`. It never changes intent correctness or rewrites responses. Detailed reports expose `format.compliance` as a non-verdict check.
- **[evaluation/output_formats.py](evaluation/output_formats.py):** readers for all eight output choices. Free-format prose that cannot be recovered is a parser gap with unknown semantic correctness, not automatically a model failure.
- **[evaluation/hosts.py](evaluation/hosts.py):** explicit host dispatch. [workbench/workflows.py](workbench/workflows.py) uses the evaluator captured in each definition; [evaluation/core.py](evaluation/core.py) supplies matching detailed diagnostics.
- **[evaluation/live_intent.py](evaluation/live_intent.py):** retained `dot-intent-v1` for frozen schema-based experiments. [workbench/live.py](workbench/live.py) remains the preparation path for those historical controls; do not use it to relabel new schema-free definitions.

New root definitions opt into the schema-free host and pin its source fingerprint. Frozen definitions continue to select their original contracts; no completed observation is overwritten or silently rescored. Configure models/runtime and verify the chosen suite before starting inference. Building/installing templates does not start inference.

On Windows, **Start Workbench.vbs** starts the UI. Python 3.10+ is required; setup asks before creating its private environment or installing missing requirements. **Start Demo.vbs** uses simulated inference, not a model-quality measurement. Both root launchers inherit the current 13-case root definition directory. **Open_Results_Table.bat** opens the review/results viewer.

Choose the models folder, install/select a suitable official llama.cpp runtime, resolve preflight issues, and run only the intended scope. GGUFs and credentials are machine-local. Native loading has no overall elapsed-time deadline; configured workflow deadlines start after readiness. Stop/Pause controls preserve completed evidence. A wrong answer is a completed benchmark observation, not a reason to reroll it.

Operational detail is in [WORKBENCH_GUIDE.md](docs/WORKBENCH_GUIDE.md), [results-table-grouping.md](docs/results-table-grouping.md), and [reporting/README.md](reporting/README.md). Those documents also retain dated implementation notes; verify the selected code and run manifest rather than assuming an older “current” count or launcher limitation still applies.

Prompt optimization is a separate workflow, not an ordinary extra dimension of every benchmark. See [optimization/README.md](optimization/README.md), [Codex writer](docs/prompt-optimization/codex-writer.txt), and [full-model coverage](docs/prompt-optimization/full-model-coverage.md). Older optimization pilots remain historical evidence; current scope is the five-operation 21-case suite. Do not resume an old session or promote a candidate merely to browse the repository.

## Editing and verification

Read [AGENTS.md](AGENTS.md) for development rules and dated scope decisions. Keep unrelated work and immutable research evidence intact. Never put private records, credentials or model weights in this public repository.

- Prompt/task changes: edit the source for the intended method, export to a new run, inspect complete prompts and review their exact digests. Do not silently regenerate a frozen cohort.
- Grammar changes: edit canonical grammar sources, regenerate the shared artifact, then check all language implementations.
- Evaluator changes: use a new version/fingerprint and separate run/analysis. Old observations must retain their original identity.
- Operational-only changes: review identity preservation; [operational-source-compatibility.json](workbench/operational-source-compatibility.json) is an exact reviewed allowlist, not permission to mark arbitrary changes equivalent.

Core software checks (from the repository root, with requirements installed):

```sh
python -m unittest discover -s tests -v
node intent-parser-js/build-grammar-spec.cjs --check
node intent-parser-js/run-all.cjs
dotnet run --project intent-parser-csharp -- self-test
```

See the language READMEs for cross-language fixtures and differential checks. These deterministic tests do not run the research models. Browser smoke tests and the identity-preservation audit are defined separately in [.github/workflows/tests.yml](.github/workflows/tests.yml); passing a local unit suite does not establish that every CI stage passed. [GRAMMAR-VERIFICATION.md](intent-parser-js/GRAMMAR-VERIFICATION.md) and [live-intent-validation.md](docs/live-intent-validation.md) record what was actually tested for those checkpoints.
