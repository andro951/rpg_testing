# System design and intended requirements

## Research purpose and scope

The benchmark asks a model to transform an existing structured state using established new information. It evaluates exact final state and collateral changes, while retaining malformed answers and failures as evidence. The intended eventual application is Ember Adventures, but docs/RESEARCH_ROADMAP.md explicitly prioritizes general inventory, household and support-ticket state management. Retrieval, longitudinal commitment timing, working/episodic memory and fixed round-cache experiments remain research directions. The existing step engine can express bounded decomposition, verification and narration examples; it does not implement a full autonomous RPG or memory database.

Current tracked inputs comprise 59 enabled test definitions and 387 cases for each eligible model. Three presentation families compare ordinary JSON, arrays displayed as numeric-key objects, and explicit full-path text. Four wording-calibration tests compare controlled prompt variants and deterministic repetitions. The suite also includes 100-item support-ticket lookup/patch tasks, household clothing transitions, stock arithmetic, booleans/enums and unconstrained dialogue. Tests with no fixed final-state oracle remain distinguishable from exact-state tests.

## Startup and ownership

Windows launchers invoke bootstrap.pyw. Bootstrap inspects Python >=3.10 and jsonschema availability, creates .venv-workbench only through its graphical setup path when needed, and launches the supervisor. launch_workbench.py runs a child interpreter and forwards stop/scheduler signals. HostLock holds an OS lock in .local/workbench or .local/demo, so process death releases ownership. A second graphical launch opens the existing worker; it can request restart when the running source commit differs. This process supervision prevents Python imports from changing during a measurement.

The active Controller owns settings, operations, result store, discovered models, reports, live state, logs, telemetry and backend lifecycle. A single operation lock prevents concurrent run, scan, downloads and most edits. An RLock protects snapshots/logs/progress. Background work uses daemon threads. setup/native file pickers are host-side actions; remote clients enter paths belonging to the GPU host. Native dialogs themselves are not benchmark operations.

Real startup uses .local/workbench/settings.json; demo uses .local/demo/settings.json. Defaults select llamacpp, an unset model root, source synchronization enabled for real runs and result publishing disabled. Secrets are omitted from settings snapshots. Runtime caches are fixed under the repository. Legacy results are migrated to tracked results/ without overwriting conflicting bytes. The catalog is machine-local root models.json, ignored by Git, containing a models-only array and required_vram_gb assignments. No model weights are committed.

## Browser and control API

WorkbenchServer serves frozen copies of index.html, app.js and style.css, authenticated /api endpoints, and a browser-neutral Controller. The browser takes a pairing key from the URL fragment or session storage; it removes the fragment after reading. State polls every 1.2 seconds. Pages provide overview, two targeted run modes, installed models, Hugging Face discovery, runtime selection, test JSON editing, raw results, comparison, logs and worker setup.

The control server binds only loopback or a 100.64.0.0/10 address returned by Tailscale. Host and Origin checks plus a constant-time bearer comparison protect APIs. Static assets are public but carry CSP/frame/content-type controls and no embedded key. Pairing-key display and native pickers require loopback callers. Inference remains an authenticated loopback llama-server endpoint on port 1235. The API does not expose an arbitrary shell-command endpoint. Enabling Tailscale persists the approved binding preference and restores it on later launches.

Disk-backed tests/results/analysis/export are blocked during operations. Live snapshots remain available. Result inspection loads full JSON evidence; exports include raw results, logs, preflight reports and CSV/JSON summaries, while excluding settings/credentials. The UI renders remote/model strings with textContent instead of HTML interpolation. The operation lock is a sequencing guard, not a transactional database; native picker/shutdown/remote checks have some check-then-act windows described in the risks document.

## Model discovery, identity and downloads

inventory.scan_models recursively inspects the explicitly selected root for GGUFs, skips symlink files and multimodal projector names, groups split shards, matches catalog filenames, and uses repo/revision parent paths to resolve ambiguous filename matches. It reads metadata from the first shard, detects missing shard names and totals file sizes. GGUF parsing checks header/version/counts and skips large tokenizer arrays; it does not validate all tensor bytes or each shard's full content.

Successful authoritative scans reconcile missing catalog entries and artifact registry assignments while retaining historical results. An unavailable root is not intentionally treated as an empty inventory. A present but empty mounted directory is still treated as authoritative, a limitation for removable storage. Uncatalogued complete models can be assigned one of the supported tiers; recommendations use estimated download footprint and headroom, never measured fit.

Preflight artifact identity records filename, byte size and mtime plus known publisher repo/revision/hash data. It avoids hashing gigabytes at every run. Replacements with changed metadata produce new identities. Identical size/mtime replacement can evade this cheap identity; publisher hashes retained in metadata are not independently revalidated on every manual rescan. These limits must remain explicit in research claims.

HubClient reads bounded HTTPS Hugging Face metadata, groups GGUF variants, requires immutable repo revisions and handles shard completion. A selected download is drawn from server-issued metadata, written directly under the chosen root/repo/revision, resumed from partial bytes with Range checks, verified against expected hashes when available, inspected as GGUF and renamed into place. Redirects cannot downgrade to HTTP and authorization is stripped on cross-host redirects. Existing files are not intentionally overwritten. Cancellation retains partial bytes. A failed download writes catalog metadata before transfer, which subsequent reconciliation can remove if no final GGUF exists.

## Native runtime installation and load qualification

runtimes.py browses official ggml-org/llama.cpp release assets, filters host/architecture GPU builds and optionally associates matching cudart archives. Installation stays under .local/runtime. It restricts URLs, bounds archive/download sizes, validates extraction paths and symlinks, identifies exactly one server executable and writes a manifest of file hashes. Reusing that installation verifies its manifest. These are supply/integrity checks, not proof of driver/device compatibility. Existing externally selected binaries are trusted by explicit host-path selection.

NativeBackend requires relevant command controls and a GPU device listing. It refuses an already-used port and launches an owned process with all GPU layers for primary work, fitting off, one slot, finite automatic context, no context shift, no output-token cap and reasoning off. It strips implicit llama/HF/GGML environment knobs and uses private cache locations. CUDA masking follows detected or Slurm-provided visibility. Vulkan device mapping rejects ambiguity and does not run under Slurm as a substitute for CUDA allocation.

Load qualification drains and retains runtime logs, checks health, reported GPU-layer/KV placement, owned alias, runtime context, and a liveness generation. Full-GPU placement is based on backend diagnostics; CPU-mapped or host-pinned buffers alone are not proof of layer offload. Unknown placement is rejected. A 600-second load watchdog cancels and terminates the owned process. The subsequent three-generation seed diagnostic is outside that watchdog today (B02), even though it is outside case timing as intended.

Chat templates are applied through the native server before tokenization and completion. The compatibility helper should adapt unsupported system roles and strict user/assistant alternation while recording exact adapted messages. Its current regex and separator escapes are defective (B01/B04). The actual messages sent and adaptation metadata are retained when adaptation occurs.

## Test contracts and prompt construction

domain.validate_test enforces schema_version 2, steps workflow, positive timeout/repetitions, safe IDs, valid presentation/style modes, supported sampling ranges, local JSON-schema references, bounded loops and prior-output references. Each variant declares generation steps, conditional execution, optional assignment, result representation and objective checks. Ground truth belongs outside source; declared expected state is schema-validated when a state schema exists. The validator still allows incomplete source/result/check contracts that fail later (R03).

Prompt generation is distinct from scoring. Conversational styles present Current State and New Information; direct-text variants send exact authored prompts. Legacy wording preserves historical SOURCE/indexed formatting. Prior outputs are included only when uses declares them. Missing conditional outputs get an explicit placeholder. Repetition zero preserves the base seed; later repetitions add 0x9E3779B1 modulo 2^32. Variant/presentation pairs share effective seed schedules for comparison. One-example wording is a generic example, not a fixture's expected patch.

workflows.execute interprets the steps in memory. Conditions use JSON-aware equality. Loops are bounded, can replace previously generated outputs and stop on explicit equality. Per-step schema-constrained outputs are parsed with duplicate/nonfinite rejection and validated after generation. A wrong answer, malformed JSON or schema-invalid response is a completed benchmark outcome; it is not rerolled for accuracy. Infrastructure exceptions retain partial calls/outputs/events for the scheduler.

## Planning, identity and resumability

planning.pending_plan serves preflight and execution. It validates model/test selections, applies assigned/adjacent GPU-tier eligibility, computes stable case IDs and consults ResultStore. IDs combine engine/workflow fingerprint, model artifact, selected test/variant, repetition and target hardware/software/context recipe. Increasing repetitions or adding neighboring variants preserves existing selected-variant identities. Changing the selected experiment or fingerprint normally creates new IDs. Targeted and full runs use the same identity and context recipe.

Automatic context uses the entire enabled suite so resume/targeted work does not change allocation. It estimates source/shared-prefix/instructions/step bytes, adds generous continuation room and clamps to native metadata. Current recipe is 65,536 tokens before native clamping. Full-path companions omit redundant authoritative source from planning to preserve existing recipes. Actual server tokenization guards input. Context exhaustion retries from the beginning with up to two larger allocations; earlier attempts and actual load context remain recorded.

One JSON file per model/case is authoritative. Atomic writes fsync temporary bytes then replace the destination. Checksum, status and filename/record identity are verified. Completed results cannot be overwritten. Earlier error/aborted/skipped attempts are retained when updating a non-completed file. Deleting a case deliberately removes completion and history. Skips are terminal except eligible primary memory failures with unfinished fallback. Hybrid identities are derived separately. Timeout-only compatibility allows earlier non-timeout completions to stay done and longer watchdogs to reopen old timeouts; it currently mishandles skipped recovery (B03).

## Scheduler and measurement boundary

Session processes all primary model groups before deferred recovery. It loads/qualifies, executes pending cases, pauses between cases on request and saves outcomes outside timing. Memory/CPU-placement failures record primary qualification skips, unload and defer; unrelated runtime/unknown-placement failures terminate that model's work without endless retry. Deferred models are sorted smallest downloaded footprint first. Recovery retries full GPU, then tries at most four positive hybrid GPU-layer counts. Hybrid outputs stay separate from full-GPU evidence.

Every test has a positive timeout_seconds, currently 60 for bundled tests. The watchdog encompasses all workflow calls, branches and orchestration, preserves streamed partial output on expiry, records a terminal failed timeout and resets the slot or reloads before proceeding. It cancels only the request during case timeout; load stalls terminate the process. Stop now cancels transport and owned process; stop after model and pause are explicit controls. Disk/result failures can stop the application because reliable evidence cannot be claimed without persistence.

Pipeline timing covers model requests and orchestration. Scoring, serialization, log flushing and Git publishing occur afterward. Sampling uses NVML in a background thread with bounded in-memory samples and pre/post case boundary readings. Device memory includes display/other processes, may miss short peaks and is not per-model or independent physical-residency proof. Missing counters remain None/unavailable. Native raw chunks retain text, reasoning, usage, finish reason, timing and cache evidence.

Controlled cache variants erase the slot before the workflow; cache-off requires all reuse counters zero, and cache-on requires a cold first call plus sufficient later reuse. Missing/inconsistent counters invalidate measurements. Default cache behavior is separate. The research roadmap's immutable round-base cache is not implemented by this single-slot reuse mechanism and remains planned.

## Scoring, comparison, Git and cluster paths

scoring applies RFC 6902 or documented semantic operations to deep copies and compares final states, not textual patches. JSON equality distinguishes booleans from numbers, treats 1 and 1.0 numerically equal and preserves list order. Field-change metrics treat arrays as one field; exact match still compares all elements. Some tasks explicitly require operation types/order, keeping state_exact_match separate from operation success. Objective checks and answer maps support lookup/narrative tasks without inventing a fixed oracle.

analysis separates artifact/test/protocol/context/placement/hardware/software/simulation groups. Eligible completed results contribute accuracy/timing, including terminal timeout failures. Invalid cache measurements are excluded. Median/nearest-rank p95 are descriptive; there is no population inference. Attempts and skips remain counted. Large result payloads are fully loaded and exported in memory, a scaling cost.

Optional source sync performs fast-forward-only pull before run; changed source triggers a fresh supervisor process and bounded saved Run intent, retaining targeted selection. Result Publisher mirrors results/logs into a worker-specific branch using narrow staging, no stash/reset/force push. Local failures retain data. The active publisher does not merge remote concurrent updates automatically; branch ownership must remain single-writer.

Unity script generation requests a single GPU, permits reviewed constraints/partitions, starts --batch only under Slurm, and forwards advance termination warnings to retain evidence. It does not provision cluster access, storage or model/runtime installations. Batch source-update restarts lack the graphical coordinator's bound (R04). Actual Unity signaling, Tailscale routes, native GPU performance, cache counters and driver compatibility require separate environment validation.

The legacy rpgbench engine uses fixed initial context/output limits, LM Studio/native managed backends, append-only attempts and optional result branches. It remains independently tested and must not be substituted for active workbench measurements. There are two scoring/storage implementations with different contracts; repairs should preserve historical reproducibility or explicitly version it.
