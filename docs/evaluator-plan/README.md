# Detailed evaluator plan

Implementation status: see [implementation review](implementation-review.md) and [per-variant review records](review.json). The document below preserves the original planning baseline.

Planning only, October 8, 2026. No evaluator, prompt, scoring rule, result, judgement or benchmark execution was changed. Scope: all 58 current test definitions, all 175 variants, the existing scoring/reporting path, and three inactive example definitions. Objective coverage is 42 definitions / 159 variants / 309 variant-repetition cases. The other 16 definitions / 16 variants / 48 cases are dialogue without fixed-answer oracles. All current definitions are enabled; the judgement catalog currently has no entries, so they start in Needs review.

## Deliverable and scope

Each test gets an explicit evaluation contract and an individually reviewed evaluator entry. Entries may share functions and parameterized family evaluators. Every variant is tracked because representation, operation requirements and workflow steps differ within a test. We will not create 58 nearly identical implementations or infer success rules from test names alone.

The deliverable is binary PASS/FAIL for objectively decidable responses, with a detailed list of passed, failed, not-evaluated and not-applicable checks. Execution outcomes remain separate: infrastructure error, stopped, incomplete timeout, missing evidence and open-ended/unscored are not silently converted into semantic failures. There is no partial-credit score or automatic acceptance/rejection of tests. Dialogue remains separate from objective totals and prompt optimization until its evaluation rubric is agreed.

`coverage.md` tracks every definition; `contracts.json` records every variant, source hash and current oracle/operation/workflow declarations. These are planning records, not registered or implemented evaluators. No benchmark observations are generated by this plan.

## Existing components to preserve

- `workbench/scoring.py`: strict whole-response JSON parsing, duplicate-key rejection, JSON Pointer parsing, array indexes, patch application on a copy, typed equality, expected-state comparison and aggregate change diagnostics.
- `workbench/workflows.py`: declared output schemas, exact expected answers, ordered `required_ops`, objective checks and multi-step/branch/loop execution.
- `reporting/report.py`: supplemental distinction between exact index answers and correct integer tokens in the wrong output format. This is deliberately not a replacement for exact-match scoring.
- Immutable saved calls contain actual sent messages, outputs/chunks, result definitions, timing and execution errors. Evaluation of saved runs must use their captured definition, not today's edited source. Current definitions may be compared explicitly in a separately labeled assessment.

Current limitations: state scoring catches exceptions into one short error; answers mostly report booleans; patch-op matching reports ordered names separately but does not explain the failure; state diffs treat changed arrays as entire values; intermediate free-text analysis has no fixed oracle; workflow step failure can prevent later checks. These are the gaps the detailed diagnostics need to address.

Keep new diagnostic implementation outside files that participate in the inference fingerprint. Initially add a versioned read-only assessment layer, leaving original exact-match outcomes and evidence intact. If a diagnostic exposes a scorer/spec disagreement, record it for review rather than changing historical results or silently tightening acceptance. New required operation/format constraints need an explicit contract decision. A diagnostic output change must not reopen completed benchmark cases or alter deadlines, prompts, provider deduplication or scheduling.

## Common evaluation pipeline

1. **Evidence and execution:** identify record, model, definition, variant, step and iteration; distinguish complete output, partial output, missing output and provider error. Preserve exact message roles/content and raw text. Do not conflate correct timing with correct content.
2. **Declared response format:** choose the contract before parsing. Index tests require literal text; patch tests require JSON arrays; typed example steps require their declared JSON type. Do not strip fences, extract a convenient JSON fragment, repair text, normalize whitespace or coerce values to manufacture a pass.
3. **Structure and local constraints:** validate operation object, recognized operation name, required fields/types, pointer syntax/escapes and declared operation count/order. Extra fields must follow the actual existing contract; do not invent stricter rejection merely because an example omits them.
4. **Path resolution and sequential application:** apply to a copy of the authoritative nested state. Distinguish malformed pointer, missing field, missing ancestor, non-container parent, invalid index, out-of-range index and illegal append position. Evaluate each operation against the state produced by prior successful operations, especially move/remove. Preserve input presentation as context, never as the authoritative state.
5. **Task-specific meaning:** verify target entity, requested value/type, insertion/removal/copy/move relationship, expected precondition, arithmetic, time advance and explicitly unchanged tracked fields.
6. **Final state and response constraints:** compare with the fixed expected state, then explain missing changes, wrong values/types, unsupported changes and array membership/order/content errors. Equivalent patches pass when the contract permits them; exact operation sequence is required only where declared or separately agreed.
7. **Assessment:** one overall objective outcome, a primary reason, independent secondary reasons and check-level statuses with actual/expected evidence. Report what was checked; never say downstream state correctness failed if an invalid patch prevented evaluation.

Later operations' syntax/field types and the declared operation-name sequence can still be checked independently after an application failure. Their contextual target resolution and final state cannot be claimed as evaluated after an earlier operation blocks the sequence. A property being equal to an expected value is only a value comparison, not proof it was applied to the right target. Numeric equality follows the existing scorer unless a declared schema imposes further requirements; booleans and quoted strings must not be coerced into numbers/booleans.

## Proposed assessment record

Every assessment will include evaluator/version, definition identity/hash, source record checksum/case ID, model/configuration, step/iteration, original score, objective outcome and execution outcome. Each check will include a stable code, scope (response/operation/field/final state/workflow), status, explanation, expected, actual and dependencies where appropriate. An operation number and pointer/value location must accompany patch errors. Limit summaries of large arrays to relevant differences, with a reference to untrimmed evidence; do not dump 100 records when one target/index explains the error.

Example for the actual nested-value failure:

```text
Overall: FAIL
Execution: completed response
PASS json.document: response is valid JSON.
PASS patch.array: response is an array of operations.
PASS patch.operation[0].structure: replace has string path and a value.
PASS patch.operation[0].path.syntax: /characters.Tom.mood is a valid JSON Pointer.
FAIL patch.operation[0].path.resolution: root key characters.Tom.mood does not exist.
     The displayed dot path characters.Tom.mood corresponds to /characters/Tom/mood.
PASS task.value_match: supplied value relaxed matches the required new mood value;
     this does not establish a successful update to Tom.
NOT EVALUATED final_state: operation 0 could not be applied.
```

This is a planned report, not newly executed evaluator output. The saved scorer's actual failure is `Target field does not exist`.

## Shared modules and test-specific requirements

| Component | Shared responsibility | Specific information supplied by each test |
| --- | --- | --- |
| Evidence/outcome | Completion, provider errors, missing data, partials, step history | Workflow, response step, captured execution metadata |
| JSON/type checks | Whole-document parse, duplicate keys, declared type/schema | Literal index text versus patch array versus typed step |
| Patch structure | RFC operations and semantic set/list operations | Representation; required operation names/count/order |
| Pointer/application | Syntax, escaped keys, ancestor resolution, array bounds and sequential state | Input presentation, target/source pointers and source-state containers |
| State difference | Missing/wrong/unsupported changes; typed comparisons | Original and expected states, protected unchanged data |
| Array diagnostics | Entity lookup, membership, relative order, copied contents and index shifts | Ticket IDs, clothing item, insertion relation, source/destination arrays |
| Literal index answer | Raw format, arity, integer values, ordering and range | Exact expected text and target entity; move's source/destination semantics |
| Task explanation | Why a change is required and other facts stay unchanged | Five-minute advance, unlock, mood, coat event or inventory transactions |
| Workflow diagnostics | Step-scoped outputs, skipped/unreached steps, repair history | Explicit intermediate checks and branch/loop rules |

Special cases that must not be buried in the shared state checker:

- **Move:** resolve `from` first, remove source, then interpret destination in the resulting array. Explain wrong target, wrong relative placement, or changed contents separately.
- **Copy:** preserve the source, append the complete selected record to the destination; diagnose missing/wrong copied fields, source deletion and accidental movement.
- **Test then replace:** require the captured ordered sequence `[test, replace]`, validate the precondition value/path, and identify which operation fails. A final-state match without the required precondition still fails this test.
- **Index-only tasks:** an answer such as `The index is 73` can have the correct numeric value and still fail literal output format. JSON parsing is not the primary format check. Ambiguous/multiple/negative/decimal answers must not be described as correctly identifying the index.
- **Narrative state updates:** evaluate only tracked state. Household movement and door use are not tracked fields in these household definitions, so do not invent changes for them. Inventory discussion of lowering the reorder point next month is not an approved change today.
- **Intermediate analysis:** retain and scope its exact text, but do not manufacture a semantic PASS from keywords or infer that fluent analysis is correct. With no fixed intermediate oracle, label its meaning unscored/review-only while judging the final patch deterministically.
- **Presentation:** raw JSON, indexed array views and full dot-path views must resolve to the same underlying state. Some full-path calibration variants embed the presentation directly in the step prompt while metadata says raw_json; use captured messages/provenance to explain presentation correctly.
- **Timeouts:** preserve timed-out status and partials. Only assert a semantic failure from partial text when an irreversible violation can be proved under the actual response contract. Incomplete JSON alone is not such proof. A complete-looking partial patch is not a completed model response. Document inconclusive cases explicitly and keep timeout markers.

## Contract decisions to resolve before implementation

- Some prompts name a particular operation, but their result declaration has no `required_ops` constraint. Preserve the current final-state acceptance rule initially, report instruction compliance separately, and flag any proposal to make it a new hard failure. Tests with declared `required_ops` already require the exact ordered operation list.
- The inactive narration example has an explicit intermediate `contains` check. The current workflow records such checks without automatically combining them with final exact-match scoring. Its contract review must state whether a new overall verdict includes this check; expose both results rather than silently changing the old verdict.
- Semantic operations and RFC JSON Patch have distinct operation contracts. Shared state comparison does not make their operation syntax interchangeable. Family helpers must select the representation declared by the variant.
- A timeout can have a provably wrong partial answer or insufficient evidence to judge semantics. Record execution status independently and document the proof required for each partial-output diagnosis; do not treat unfinished JSON as a complete invalid answer.
- Dialogue has no deterministic semantic oracle. Its rubric and any human/model judgement approach require a separate decision; all 16 definitions remain explicitly pending.

These are identified review points, not changes made by this planning work. Most objective contracts can use the existing oracle immediately; an ambiguity blocks only the affected entry.

## Implementation order

First freeze the complete inventory and confirm each variant's acceptance contract. Then build only the common primitives demonstrated as necessary by this inventory, with small positive/negative fixtures. Finish test-specific evaluator entries one definition at a time in this order:

1. Scalar updates: time, boolean, nested mood, across their normal/indexed/full-path and prompt-version variants. The discussed nested/full-path case is the first pilot only after the common contract design is complete.
2. Clothing append and remove, then household coat variants: array changes, semantic versus JSON Patch operations and unchanged-state checks.
3. Inventory net stock: arithmetic, required replace and ignoring hypothetical changes.
4. Eight index-only definitions: raw answer format, exact versus diagnostically correct values, target lookup and move pair ordering.
5. Six 100-item patch operations, each with its companion full-path definition: replace, remove, add, move, copy, test-then-replace. Use identity-aware array diagnostics instead of a flood of shifted-index differences.
6. Finish workflow overlays across every two-step variant, then a coverage audit across all 159 objective variants. Three inactive examples get planned contracts and future tests but are not activated as benchmarks.
7. Dialogue gets its own later rubric decision and review workflow. Keep all 16 entries visible in tracking as `rubric needed`, not falsely complete or silently forgotten.

Do not move on from an individual objective definition until every variant has its contract, coverage fixtures, saved-output assessment and human-readable diagnostic review completed. Shared helper changes require rerunning all dependent evaluator fixtures, not just the latest definition.

## Required validation for every evaluator entry

For each definition and all its variants:

1. Re-read the exact sent prompt and oracle; independently state what passing means. Verify source/oracle consistency. Flag ambiguity or evaluator limitations separately from model failure.
2. Use saved real outputs from all available models/repetitions. Include a known pass and a known failure if they exist. When no pass exists, construct a valid response from the oracle and label it synthetic; do not rerun models to obtain convenient evidence.
3. Add targeted mutations with independently specified expected diagnoses: wrong pointer syntax versus wrong target, wrong value/type, missing operation/field, unsupported changes, wrong operation sequence, array off-by-one, extra text and truncated response. Also cover permissible equivalent patches, parse/apply failures and missing/errored evidence where relevant.
4. Run the evaluator offline against the saved output and these fixtures. Inspect the resulting text/JSON and verify that every claimed PASS/FAIL/not-evaluated status is justified. Checking only the final boolean is insufficient.
5. Compare new outcome with the original saved score. Investigate every mismatch; preserve old evidence and record whether it is a diagnostic bug, existing scorer issue or a contract decision. Do not turn a discrepancy into an automatic rewrite of scores.
6. Save the reviewed example assessment and a short reviewer note with verdict, evidence references, evaluator version, fixtures/checks run and unresolved items. Mark the individual variant `reviewed` only after this review agrees with its explanation.
7. Run appropriate unit/smoke tests and the repository-required unit suite after implementation changes. Test result display/export integration only when that integration is introduced. No optimizer, new model calls or benchmark reruns are part of evaluator verification by default.

Acceptance: every objective variant is registered, every required check is mapped, every diagnostic has been reviewed on real saved evidence or explicitly labeled synthetic coverage, no invalid response receives a PASS, no inapplicable/unreached stage is claimed checked, raw data and identities remain intact, and dialogue/examples are correctly accounted for. Unresolved contract disputes block completion of the affected entry, not the entire unrelated implementation.
