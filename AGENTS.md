# Development rules

- October 15 five-operation revision: the current supported operations are Update, Append, Remove, Move and Copy. Move removes an ID/value-selected element from one collection and appends it to a different collection. Copy appends a complete independent copy to a different collection, leaving the source unchanged; IDs remain unique within each collection. Both destinations select the collection itself. Same-collection transfers and transfers into the source element's children remain unsupported. Keep five shared operation explanations in every method prompt. See docs/test-suite-v2/five-operation-coverage.txt for the 21-case coverage review; no indexing, positional insertion, reordering or test/precondition benchmarks.

- October 15 ID-only presentation requirement: new prompts use Normal JSON, ID-keyed arrays and Full paths. Dictionary views key object elements by the schema-declared ID field's value (retaining that field inside each element), and primitive elements by their own unique value. Reject colliding dictionary keys rather than lose data. Full paths display the actual output path followed immediately by a colon and JSON value, e.g. /people/"jx1b"/hair:"black"; no outer quotation marks around the path, equals signs or spaces after the separator. Empty arrays/objects remain visible. Never generate positional selections or index-returning tests. Positional renderer/evaluator code exists only to reconstruct immutable archived experiments. Standard json_patch is retired from the active builder; retain its legacy evaluator and saved evidence unchanged.

- October 15 activation: Isaac approved the exact current 14 tests / 41 prompts for normal execution (123 observations per eligible model). Prior results, optimization sessions and superseded drafts are in archives/suite-before-activation-2026-10-15; the original research definitions remain in archives/test-suite-2026-10-14. Default discovery must not scan either archive or restore its contents. Future prompt edits still invalidate their own exact approvals; this release approval is not permission to approve arbitrary future revisions.

- Prompt wording: use "element" consistently for an array/collection member, including elements that are objects or primitive values. Use "object" to name the JSON type and "field" for its named fields; do not switch between element, item, entry and record in model-facing explanations. Preserve literal data, ID values and internal field/test/template identifiers when editing prose.
- Keep the selected operation method in metadata; do not inject an "Operation method: ..." label into prompts. Use "fields" for the fields of an operation object and "How to write a path:" as the path-instruction heading.

- October 14 value-path update: the active method is value_patch. Array path parts are typed JSON values: match an object by its schema-declared ID, or a primitive element by its own value. No @ marker and no positional array selection. Parse quoted JSON strings before splitting slashes; preserve JSON types. Append/Move/Copy destinations select the collection itself. The standard json_patch legacy evaluator/results must retain RFC behavior; its positional prompt generation was retired on October 15. See workbench/value_paths.py and test_builder/methods/value_patch.txt.

- October 14 database-suite definition (expanded October 15): fixed predefined fields, unique values or declared unique IDs within every collection, complete records conforming to the collection schema, and optional ordering. Allowed task operations are Update, Append, Remove, Move and Copy between collections. No arbitrary positional insertion or same-collection reordering belongs in the current suite. Empty operation lists mean no changes are needed. Keep database rules, reusable task/data and operation-method instructions separate; every prompt for a selected operation method gets the same explanation of all five operations and that method's path format. Other operation methods remain future comparisons with ID-based collection selection. Drafts remain disabled until both assistant and Isaac approve exact prompt digests. See `docs/test-suite-v2/build-and-review.txt`.

- Treat root `models.json` as machine-local and Git-ignored. When present, keep it a models-only JSON array. Use required_vram_gb, not min_vram_gb. Memory budgets are estimates until measured under a recorded load configuration.
- Do not put fixtures' expected states or example patches into model prompts.
- A wrong model answer is a completed benchmark result, not an infrastructure retry. Never retry selectively to inflate accuracy.
- Preserve immutable raw responses, exact experiment settings, model hashes and error records. Equivalent patches are graded by final state, not textual patch equality.
- Run `python -m unittest discover -s tests -v` after each code change. Add unit/smoke tests for new behavior, including failures. Repeat the mock run to check resume.
- No real private records, credentials or model weights in this public repository. Synthetic benchmark prompts and outputs under `results/` are intentional research evidence and are version-controlled, including mature fictional benchmark content. Never stage arbitrary user directories or force-push results.
- Do not call mocked tests real inference. Do not report unmeasured timing, memory or cache hits as zero.
- Keep controlled caching, verification/repair and narrative generation marked planned until implemented AND tested.

## Perchance and provider capability standing rule

- Follow `docs/perchance-capability-policy.md` when planning, implementing, testing, or analyzing the Perchance Text Generator adapter. This is an explicit user requirement, not an optional optimization.
- When a provider cannot apply or verify an experimental control, run ONE representative baseline per distinct effective prompt/workflow/condition within each configured repetition instead of running each unsupported setting value. October 8 user update: ordinary repetitions MUST run as independent service trials even when seed effect/reproducibility is unverified; forward the requested repetition-derived seed experimentally and record it separately from applied/verified controls. Never collapse repetitions or fulfill them by reusing another repetition’s response. Record requested controls, actual applied controls, unsupported/unverified capabilities, and every collapsed case's reference to that single observation. Never fabricate support, silently ignore settings, clone scores as independent results, or count collapsed cases as additional samples. Preserve genuinely different prompts, states, representations, supported controls, workflow steps, and scoring requirements. Timeout is only an execution watchdog, never a case-identity, provider-collapse or report-row dimension. Changing it must not reopen completed cases (including terminal timeouts), clone observations or create deadline-version rows; save the actual run deadline as metadata. Feature-only measurements that cannot be performed are not applicable, never invented baseline successes. Configured repetitions are already authorized; extra unconfigured trials still require explicit user direction.
- Apply this to cache modes and verification, all sampling knobs, seed-only/reproducibility control comparisons (not ordinary repetitions), constrained output, context/token controls, execution placement and provider configuration, and any future knob. Unknown capability is unverified until demonstrated. Provider defaults are unknown unless observed, not the requested values. Unavailable measurements remain null/not applicable, never zero.
- Perchance is fixed to the 8 GB scheduling tier with an explicit exclusion of larger tiers; do not inherit the local-model one-tier-up exception. Its inference is a remote service, not measured local 8 GB GPU inference. Preserve existing local-model case identities and raw evidence when adding it. The adapter and capability-aware scheduling are implemented with unit and simulated browser coverage. One harmless Windows normal-browser/CDP text request succeeded on October 8, 2026; its diagnostic evidence is separate from study results. Full live benchmark execution and Linux/Unity deployment remain unverified; do not treat mocks or connectivity checks as scored study observations.

- User-directed clean reset on 2026-10-01: all saved benchmark results were deleted before adopting timeout-independent identity. Do not restore prior results or deadline-comparison catalogs from old report artifacts.

- Local benchmark/example deadlines are 120 seconds; Perchance always uses 300 seconds. Overview Run all includes Perchance last only on the actual 8 GB tier, after native recovery. Keep stop/cancel, combined preflight counts and terminal resume working; never rerun saved local results just because the deadline changes.
- October 9 user requirement: prompt-writing generation in Prompt Optimization has NO elapsed-time watchdog or socket read timeout, including when reasoning is enabled. Use completion, the automatically allocated finite context/output allowance, and manual Stop. Preserve partial text/reasoning on interruption. Do not reintroduce a fixed time cutoff to compensate for a slow GPU. This rule is specific to generating improved prompts; benchmark trial deadlines remain as specified above.
- October 14 user requirement: Prompt Optimization supports Local model and the worker's installed Codex. Codex model and effort are separate selectors using its actual catalog. One persistent Codex thread belongs to each optimization session and is resumed throughout that session; never silently replace a failed or foreign-worker thread. Codex proposes prompts; the existing benchmark models/evaluator test them. Record Codex's applied model/effort and unsupported sampling controls explicitly. Prompt writing still has no elapsed timeout, with manual Stop and partial evidence preserved. See `docs/prompt-optimization/codex-writer.txt`.
- October 14 user requirement: native model loading, including its readiness probe, has NO elapsed-time deadline. Wait for readiness, manual Stop or a real runtime failure; ignore legacy `load_timeout_seconds` settings. Short health requests may be retried for responsive polling, but must not become an overall load cutoff. Keep loading phase, elapsed time and last runtime activity visible and saved. Benchmark workflow deadlines begin only after loading succeeds. Preserve crash/allocation/placement checks and existing terminal results.
- Reviewed operational-only changes must preserve completed benchmark identities. `workbench/operational-source-compatibility.json` maps exact reviewed implementations to their prior experimental fingerprint; raw current source provenance is still saved in native load metadata. Do not declare arbitrary future changes equivalent. Review generation, sampling, input/context, placement and scoring behavior before adding compatibility entries.
- At the very start of preflight (also when Run invokes preflight), determine whether Perchance has pending work in the selected scope on an eligible 8 GB worker. Verify its Python dependency and local browser launch before the other readiness checks. Missing or broken setup must offer an install Yes/No popup; install only after Yes and recheck readiness. No is recorded in preflight/log evidence, skips only Perchance for that one upcoming run, and leaves its observations pending. Never persist No as a permanent setting or fake completed/skipped benchmark results. Ask again on the next run if setup is still needed. A standalone preflight's No carries into exactly one matching Run; completed, excluded, demo or larger-tier work must not trigger installation. Keep this setup lifecycle outside inference/provider identity so existing observations remain complete.
